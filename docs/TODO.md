## Code structure and tests

From a review of the architecture (October 2026). The gap behind all three items: what "Apply recommended" picks is built in two places, and the window's half has no test. Do them in this order; each is its own commit.

- **A. One plan for the window and the command line.** The Overview's checklist is built by `MainViewModel.EnsureProfile` and `ApplyProfile` (`MainViewModel.Scan.cs`); `--apply-recommended` and the first sign-in use `CommandLineApply.RecommendedPlan`. `FirstSignInTests.PlanIsTheSameForWindowAndCommandLine` calls the command line's function on both sides, so the window's path is never compared. The two differ today in three ways: ignored results are removed after the profile in the window (`WithoutIgnored`) and before it on the command line (`IgnoredResults.Without` in `ChangeSession.ScanAsync`); each picks the profile with its own code (requested, saved, suggested, offered on this PC); the window builds its first plan before the 3 second CPU sample (`waitForBackgroundSample: false`), the command line waits for it. To do: one function in Core from states, findings, facts, profile and both ignore lists to the `RecommendationPlan`, and one for the choice of profile next to `ProfileCatalog`; both callers use them (the window keeps saving the suggested profile and honoring `--profile`). Decide in one place where ignored results are removed and whether the CPU sample's check counts for the first plan. Then make the test go through the window's path. Done when the window and the command line cannot pick differently without a failing test.
- **B. Expected plans for sample PCs.** No test shows what an edit of `profiles.json` or of a tweak's `when` does to the plan. To do: three or four `HardwareProfile` fixtures in `tests/Optimizer.Core.Tests/Fixtures` (NVIDIA gaming desktop, gaming laptop, older PC, Home edition), each run through `ScanService.Evaluate` (public, no scanner needed), `FactsBuilder.Build`, `TweakEngine.DetectAll` against the registry sandbox and fakes, and the function from A for every profile the PC offers; the tweak ids are compared with a checked-in file per PC and profile, written again with `PCO_UPDATE_DOCS=1` like the VM test plan tables. Check first that `DetectAll` gives the same states on every run. Done when a catalog change that alters a plan shows up as a diff of those files.
- **C. The window's state without WPF.** `MainViewModel` (13 partial files, about 2,900 lines) is the only view model no test creates: it takes the concrete `AppServices`. After A, move the scan and plan state (`_findings`, `_tweakStates`, `_facts`, `_usage`, `_profiled`, `_profiledFindings`, `_plan`, `_drift`) and the logic around it into a plain class, and test it as `StorageViewModel` is tested: a scan requested while one runs (one more scan after it, never two at once), a laptop profile on a desktop falling back to Gaming for the session, ignored results and tweaks, reapplying reset changes. Not a split into several services: Core already holds the scan (`ScanService`), the plan (`Recommendations`), the changes (`ChangeSession`) and the backups (`BackupStore`).
- **Optional:** the developer switches take about 430 lines of `App.xaml.cs` (`SaveScreenshotsAsync`, `WritePerfReportAsync`, tab order). A move into a partial `App.Developer.cs`, only while working in that file anyway.

Looked at and left as is, so they need no second look: a startup policy class around `Program.Main` (every step there already calls its own tested class; what remains is their order, which is the policy), more interfaces around registry, services and tasks (`ActionContext` and `ArchitectureTests` cover them), versioned catalog metadata (the catalog ships inside the exe; the saved formats, backups and exports, carry versions already), more policy gates for risky changes (`IsBatchSafe`, enforced again in `TweakEngine`, edition and build conditions, `OsGate`, signed updates), and a lint for vague wording (`DocLint` covers the typography; a phrase list would mostly flag good text).
