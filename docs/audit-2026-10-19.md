# Repository audit, 2026-10-19

Main at `e275a15` (Release 1.3.0), clean tree. Scope: the app (Core and WPF), the tests and CI, the docs and the website tunero.dev.

**Method.** Seven reviewers read the code in parallel:
- six areas, file by file: core engine; platform, interop, hardware and checks; feature modules and the update path; the WPF app; tests, CI, docs and catalog content; the website, compared with the live site
- one cross-cutting reviewer for architecture, coupling, duplication and dependencies

Each reviewer started from the audit of 2026-10-13 and reported only new findings or ones still open. I re-read the code behind every medium finding and the lows that affect data or security, and dropped what I could not confirm. **Confirmed** means the code does what the finding says. **Plausible** means the code path exists, but the harm depends on something nobody could check here (an ACL on another PC, how Windows reacts). The other lows come from the reviewers and were spot-checked only.

**Baseline.** `dotnet build -c Release` built with 0 errors and 1 warning (`xUnit1031`, `tests/Optimizer.Core.Tests/AppInstallTests.cs:207`). `dotnet test -c Release --filter "Category!=Hardware"` passed all 1409 tests (1342 Core, 67 App). `npm run build` of the website passed. `dotnet list package --vulnerable --include-transitive` and `npm audit` found nothing.

## Summary

**The app is in good shape: no critical or high finding.** The apply and undo engine, the backup format with its golden fixtures, the update chain, SafeDelete, the elevation boundary, the MFT parser, the COM and P/Invoke layouts and the catalog rules held up again. Every high finding of 2026-10-13 is still fixed. Of its 1.0 blockers, one is only partly fixed: checks still disappear when a probe fails (M4).

What is left is narrower:
1. **The 1.3.0 install path** is the youngest code, and it has the most findings: a close during the install, a Start menu entry left behind after a failed start, and a signature check that pins only the subject name (M3, M5, L-A1 to L-A4).
2. **Data safety at the edges:**
   - The leftover check after an uninstall can offer the folder of another program that is still installed (M1).
   - The re-apply task can outlive an uninstall done with a package manager (M2).
3. **Checks that disappear instead of saying Unknown** when a probe fails, which raises the score (M4).
4. **Untested recovery paths:** the self-update rollback and the setup decision (M6).
5. **Release channels:** Chocolatey is approved, but only for 0.8.0 (M7).

## Medium findings

### M1. The leftover check can offer the folder of a program that is still installed, ticked by default (confirmed)

- Where: `src/Optimizer.App/ViewModels/AppsViewModel.cs:425` passes `Programs.ReferencedPaths` (`src/Optimizer.Core/Apps/Programs.cs:124-166`) to `ProgramLeftovers.FindAll` / `MayOffer` (`ProgramLeftovers.cs:218-233`).
- What is missing: `ReferencedPaths` reads only InstallLocation, the uninstall strings, DisplayIcon and service ImagePath. The orphan scan (`ProgramOrphans.ReadEvidence`, `ProgramOrphans.cs:43-63`) also reads three more sources, and its comment says why: "MSI packages often record no install location":
  - the MSI component folders of the products still installed
  - App Paths
  - COM servers
- Scenario:
  1. Program A has its InstallLocation at `C:\Program Files\Vendor`.
  2. Program B is an MSI in `C:\Program Files\Vendor\Tools`, with no InstallLocation or DisplayIcon. Its uninstall string resolves to System32's msiexec.
  3. After A is uninstalled, `Vendor` passes `MayOffer`.
  4. `LeftoverRow._selected` is `true` (`AppsViewModel.cs:144`), so one click moves B's files to the Recycle Bin.
- Fix: build `referenced` the way `ReadEvidence` does, at least the `MsiFolders` of every remaining product code, App Paths and COM servers. Leave a folder leftover unticked when it holds files of another product.

### M2. The re-apply task outlives an uninstall by a package manager and is registered again without a path check (dangling task confirmed; escalation plausible)

- Where:
  - `ReapplyTask.CanRegister` is checked with `TrustedPath.IsAdminOnlyBelowSharedFolders` (`MainViewModel.Reapply.cs:17`, `TrustedPath.cs:39-65`). That check lets folders above the exe's folder accept new entries from users (it is meant for `C:\ProgramData`).
  - Only the in-app uninstall deletes the `\Tunero\` tasks (`SelfUninstall.cs:52-57`). `choco uninstall`, `winget uninstall` and `scoop uninstall` leave them.
  - `OwnTaskAction.Apply` (`Actions/OwnTaskAction.cs:34-37`) checks only the task path, not the exe in the XML. Drift re-apply ("Apply again", `--reapply`) registers the stored XML again whenever the task is missing or runs another command.
- Consequence:
  - Confirmed: after a package-manager uninstall, a task with highest privileges starts a missing exe at every sign-in.
  - Plausible: if a folder above the removed one lets users create folders, a standard user can recreate the path and plant `Tunero.exe`, which then runs elevated at the admin's next sign-in. Chocolatey's default ACL on `C:\ProgramData\chocolatey` should prevent this, so it needs a changed ACL or another install root.
- Fix:
  - Register and re-register only for `TrustedPath.IsAdminOnlyWritable`, which is strict all the way up.
  - Check the `<Command>` of the XML in `OwnTaskAction.Apply`.
  - Add uninstall hooks (Chocolatey `chocolateyBeforeModify.ps1`, a Scoop `uninstaller` script) that delete the `\Tunero\` task folder.
  - Until then the README tells users to turn the task off first (done in this audit).

### M3. The install's signature check pins the subject name, not the issuer or root (confirmed in code; attack plausible, defense in depth)

- Where: `AppInstall.IsTrustedFile` (`src/Optimizer.Core/Platform/AppInstall.cs:48-60`) accepts any WinVerifyTrust "Signed" result whose subject string is in `TrustedPublishers`. The check runs without revocation and with cache-only retrieval (`Startup/SignatureVerifier.cs:284-293`).
- Scenario:
  1. A process of the same user swaps the downloaded exe for one signed with a self-made certificate that has the same subject name. Its root sits in `CurrentUser\Root`; adding it there shows a Windows prompt.
  2. The install copies that file to Program Files and starts it elevated.
  3. The re-apply task then keeps starting it.
- Limits: such a process could also swap the exe before the user starts it at all. The check matters most once the user has checked the signature in Properties, so this is hardening, not an open door.
- Fix: build the chain with `X509Chain` and `TrustMode = CustomRootTrust`, with the Certum root (and ideally the intermediate) pinned, the code-signing EKU required and the subject check kept.

### M4. Whole groups of checks disappear when a probe fails, instead of showing Unknown (confirmed; partly still open from M5 of 2026-10-13)

- Where:
  - `StorageProbe.Read` (`src/Optimizer.Core/Hardware/Probes/MiscProbes.cs:41-75`) queries WMI (`Wmi.PhysicalDisks`, `MSFT_Partition`) before it reads `DriveInfo`. A WMI failure or timeout loses the volumes, which need no WMI.
  - F17 low disk space then returns nothing (`MemoryStorageChecks.cs:252`, `if (p.Storage is null) yield break;`).
- Also lost with a failed probe:
  - from the storage probe: F12, F18, A.systemHdd and F28 drive health (which can be Critical)
  - from the memory probe: F13, A.xmp and the other memory checks
  - from the power probe: F8, F9 and F19
  - from the extras probe: F14, F15, F16 and F25
- Result: the readiness score goes up, and the error shows only on the System info page.
- Fix:
  - Catch the WMI part in `StorageProbe` and still return the volumes.
  - Have each check yield one Unknown when its source is null or failed.
  - Use null for "not read" in `DiskHealth`, not `[]`.

### M5. Closing the window or signing out during the install is not blocked (confirmed)

- Where: `Views/MainWindow.xaml.cs:48-53` and `App.xaml.cs:61-69` block only while `ChangeGate.Instance.Busy`. `InstallService.InstallAsync` (`Services/InstallService.cs:46`) runs `AppInstall.Install` in `Task.Run` without setting it.
- Scenario: Alt+F4 during the 70 MB copy and check ends the process. It leaves `Tunero.exe.new` or a fresh Program Files folder behind.
  - With an earlier install, the close can come between `File.Move(exe, .old)` and `File.Move(.new, exe)` (`AppInstall.cs:161-166`).
  - The entry, the Start menu entry and the re-apply task then point at a missing exe.
- Fix: set `ChangeGate.Busy` around the install step, or cancel Closing and SessionEnding while `SetupBusy`.

### M6. The self-update rollback and the setup decision have no test (confirmed)

- `Updater.RollBack` (`src/Optimizer.Core/Updates/Updater.cs:173-190`) and the restore branch of `Updater.Install` (`:129-145`) are called by no test. The VM row "failed self-update start" (`docs/vm-test-plan.md:72`) is still empty.
- `UpdateService` creates `new Updater()` and uses `DataPaths.Updates` itself (`Services/UpdateService.cs:108-170`), so its "Update now" path cannot be faked.
- `MainViewModel.Setup.cs` holds the setup decision (`OfferSetupAsync`, `:67-95`; it calls `ShouldOffer` with hard-coded `true, true` at `:93`) and the finish steps (`:115-133`). It depends on a static `SystemRegistryRoots` (`:18`) and `AppInstall.DefaultFolder`.
- Consequence: the only paths that recover a user from a blocked new exe, and the logic that decides who sees the setup screen, have never run under test.
- Fix:
  - Temp-folder tests for `RollBack` and the restore branch.
  - Inject the downloader and updater into `UpdateService`.
  - Move the setup decision into `InstallService` with the registry, folder and Start menu injected.

### M7. Chocolatey serves only 0.8.0, which is unsigned and four releases old (confirmed)

- The community feed shows `tunero` 0.8.0, approved 2026-10-15 16:10. The pushes for 1.0.0 to 1.3.0 were refused with 403 while 0.8.0 waited; the 1.3.0 run at 13:18 the same day ended with the workflow's own notice to run it again by hand.
- `choco install tunero` installs 0.8.0 today, and "Update now" in that copy runs `choco upgrade`, which finds nothing newer.
- Fix: run the chocolatey workflow by hand for v1.3.0 (assigned to the owner as a task), then set `choco live:true` in `website/src/lib/data.ts` once a current version is approved.
- The winget PR (microsoft/winget-pkgs#450585) is still open.

### M8. "Already in place" for tweaks that do not apply to this PC (confirmed)

- Where: `src/Optimizer.Core/Tweaks/TweakEngine.cs:353` returns `NothingToDo` when no action reads NotApplied. That includes every action reading Unsupported, and a tweak whose actions expand to none (no network adapter, a read that failed).
- `ChangeTransfer.Plan` (`Backup/ChangeTransfer.cs:189-194`) does not filter on state.
- Scenario: Import or `--apply` of `network.nicPowerSavingOff` on a PC with Wi-Fi only reports "already in place" and counts it as skipped. The same happens when DISM or WMI fails between the scan and the apply.
- Fix: return Blocked with an "unsupported or unreadable on this PC" reason when nothing reads Applied either, and count Unsupported as not for this PC in `Plan`.

### Owner decision: C2PA metadata in the icons (confirmed)

- `website/public/favicon.svg`, `website/src/assets/tunero-icon.svg`, `docs/brand/*` and `src/Optimizer.App/Assets/app.ico` (and the icon PNGs) embed a C2PA manifest. The manifest is signed "Anthropic Claude Content Signing" and says Claude provided the file.

## Top 5 refactors

1. **One process runner in `ActionContext`** (M6, L-E1, L-E3).
   - Today: `StreamingProcess` is static, and the winget, SFC/DISM and PresentMon flows call it directly (`Winget.cs:126, 154, 262`, `HealthTools.cs:14-22`, `AppsViewModel.cs:552`). `IProcessRunner.Run` has a timeout but no cancellation.
   - The change: one `RunAsync(file, args, timeout, CancellationToken, IProgress<string>)`, with the architecture test extended to `src/`.
   - Payoff: fakes and tests for install, upgrade and repair, a Stop button for long DISM runs, and one timeout policy (no kill during servicing).
   - Effort and risk: one to two days, low to medium (per-tool encodings).
2. **Own-task lifecycle** (M2).
   - The change:
     - The strict path check for registering and for re-registering.
     - A `<Command>` check in `OwnTaskAction.Apply`.
     - Chocolatey and Scoop uninstall hooks that delete `\Tunero\`.
     - A VM plan row.
   - Effort and risk: half a day, low.
3. **Probe results with "not read" distinct from "empty"** (M4).
   - The change: every probe returns what it could read with a per-section error, and every check yields Unknown for a failed section.
   - Payoff: the score cannot rise because a probe failed, and a full system drive is always reported.
   - Effort and risk: one day, low.
